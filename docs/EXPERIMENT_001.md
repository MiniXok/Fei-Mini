# Experiment 001: Learned Search vs Deterministic Search in Verified Relational Space

## 1. Research Objective & Hypothesis

**Hypothesis:** A small learned policy that ranks candidate operations or programs can navigate a bounded executable program space more efficiently than deterministic enumeration and random search, while preserving independent correctness verification.

**Primary Question:** Can guidance reduce the computational cost (candidate executions, CPU time, wall-clock time) of discovering a semantically correct relational program without being trusted for correctness?

We evaluate:
1. **Exhaustive Enumeration:** Systematically generates well-typed programs in order of increasing AST complexity/depth with canonical pruning.
2. **Random Search:** Samples valid well-typed programs uniformly or grammar-weighted with fixed seeds.
3. **Learned Search Ranking:** (Post-M4 gate) Guides search step-by-step.
4. **Direct Generation:** (Post-M4 gate) Direct AST synthesis.

**Critical Scientific Safeguard:** The engineering agent is not the subject being evaluated. All ground-truth programs, schemas, tables, and test splits are generated by deterministic code. Solvers never receive gold programs or hidden evaluation instances.

## 2. MiniRel Relational DSL Specification

MiniRel is a compact, strictly typed relational query language with explicit AST nodes and an in-memory execution engine.

### Types
- `Type`: `INT`, `FLOAT`, `STR`, `BOOL`
- `Column`: `(name: str, type: Type)`
- `RelationSchema`: Ordered list of `Column`s, with optional primary key / foreign key metadata.
- `Table`: In-memory relation consisting of a `RelationSchema` and a sequence of typed immutable rows (tuples).

### Operators
1. `SCAN(table_name)`: Scans a named table from the database context.
2. `FILTER(input, column, op, literal)`: Evaluates row predicate where `op in {EQ, NEQ, LT, GT, LTE, GTE}`.
3. `PROJECT(input, columns)`: Projects subset of columns; preserves row count.
4. `JOIN(left, right, left_col, right_col)`: Inner equijoin producing concatenated tuple attributes with disambiguated column naming.
5. `GROUP_BY(input, group_cols)`: Groups rows by specified key columns.
6. `SUM(input, agg_col, as_col)`: Aggregates a grouped relation by computing sum on numeric column `agg_col`.
7. `COUNT(input, as_col)`: Aggregates row count for grouped or whole relation.
8. `SORT(input, sort_col, direction)`: Stable sort by column values (`direction in {ASC, DESC}`).
9. `LIMIT(input, count)`: Takes the top `count` rows (integer literal > 0).

### Semantic Guarantees
- **Row Ordering:** Preserved unless `SORT` is applied.
- **Empty Relations:** Valid; schema is preserved.
- **Type Checking:** Pre-execution static validation. Type errors or unknown column references reject AST prior to evaluation.
- **Equivalence:** Two tables are equivalent if they have identical schemas (names and types) and identical rows in the same order (or multiset equality if order is unspecified, but MiniRel default is deterministic row comparison).

## 3. Task & Database Generation

- **Databases:** Relational instances generated deterministically with schemas (e.g. 2-3 tables, foreign keys, varied domains: integers, floats, categorical strings).
- **Tasks:** A target relational query defined as a gold AST.
- **Instances per Task:**
  - 3 visible training/demonstration database instances (`examples`) with inputs and expected output tables.
  - 3 hidden validation database instances (`hidden_instances`) used strictly by the independent verifier to check semantic generalization (preventing spurious overfitting to small examples).
- **Dataset Targets:**
  - Train: 1,000 tasks
  - Dev: 200 tasks
  - Test: 200 tasks (hash-locked)

---

## 4. Leakage Prevention & Dataset Splitting

- Splitting is performed across **schema families and compositional operator profiles**, not random row splitting.
- The test set contains hold-out schemas, unseen operator compositions, and longer chain lengths.
- The test set is written to `datasets/test/` and locked with `datasets/test_manifest.json` containing SHA-256 hashes of all task files.
- Automated tests verify that solvers cannot access `gold_ast` or `hidden_instances`.

---

## 5. Solver Interface

All solvers inherit from `BaseSolver`:
```python
class BaseSolver:
    def solve(
        self,
        task: TaskSpec,
        budget: SearchBudget,
    ) -> SearchResult:
        ...
```
`TaskSpec` exposes:
- `schemas`: Dict[str, RelationSchema]
- `examples`: List[Tuple[DatabaseInstance, Table]]

`SearchResult` records:
- `best_program`: Optional[ASTNode]
- `solved`: bool (based on visible examples)
- `candidates_generated`: int
- `candidates_type_rejected`: int
- `candidates_executed`: int
- `cpu_time`: float
- `wall_time`: float
- `trace`: List[CandidateEvaluationRecord]

---

## 6. Verifier & Diagnostic System

The `Verifier` evaluates candidate programs against:
1. `AST_VALIDITY`: Syntactic correctness.
2. `TYPE_VALIDITY`: Schema and column type safety.
3. `EXAMPLE_CONSISTENCY`: Matches all visible examples.
4. `HIDDEN_GENERALIZATION`: Evaluates candidate on hidden database instances and compares against expected output.

Diagnostics include:
- `TYPE_MISMATCH`, `UNKNOWN_COLUMN`, `INVALID_JOIN`, `INVALID_AGGREGATION`, `EXAMPLE_MISMATCH`, `GENERALIZATION_MISMATCH`, `EXECUTION_TIMEOUT`.

---

## 7. Evaluation & Budgets

- **Candidate Budgets:** 32, 128, 512, 2048 evaluations.
- **Wall-clock Budgets:** Per-task timeouts (e.g. 5.0 seconds).
- **Metrics:**
  - Example Solve Rate (% tasks matching all visible examples).
  - Generalization Solve Rate (% tasks matching hidden instances).
  - False Acceptance Rate (% tasks solving examples but failing hidden instances).
  - Candidates executed per solved task.
  - CPU time / Wall-clock time.
  - Memory consumption.

## 8. Milestone Gates

- **M0:** Architecture & Spec (Complete).
- **M1:** MiniRel AST, Interpreter, and comprehensive operator test suite.
- **M2:** Task & DB Generator, Test manifest lock, Leakage tests.
- **M3:** Exhaustive and Random Search baselines implementing common interface.
- **M4:** Benchmark runner, empirical baseline characterization on dev/test sets, Baseline Report.
- **GATE:** Stop at M4. Model training occurs only after baseline characterization proves search hardness and necessity.
